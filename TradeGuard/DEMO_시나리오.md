> 소요 10분 · 비용 0원 (LLM 호출 없음)

## 시작

```bash
cd ~/KB/TradeGuard
pip install -r requirements.txt     # 최초 1회
bash demo.sh
```

- **http://localhost:8000/** ★ **실동작 앱** — 업로드 → 판독 → 하자 검사 → 환노출이 한 화면에서 실제로 돌아갑니다
- http://localhost:8000/mockups/ — 정적 화면 모음 (개별 화면 확인용)

> **발표 직전에 반드시 이걸 한 번 돌리세요.** 화면이 모두 최신 판정 결과로 갱신되고,
> 환율도 그날 시세로 바뀝니다. LLM 호출이 없어 비용은 0원입니다.

## 장면 0 — 실동작 앱 (★ 이걸 먼저 보여주세요, 3분)

**http://localhost:8000/** 에서 전 과정이 실제로 돌아갑니다.

### ① 샘플 케이스 모드 — 비용 0원, 실패 위험 0

케이스 카드 3개가 등급 순으로 놓여 있습니다. **CLEAN-017(A) → DEFECT-019(C) → DEMO-001(D)** 순으로 눌러보세요. 누를 때마다 즉시:

- 위험 등급 카드 (A~D · 점수)
- 하자 목록 (UCP600 조항 인용 + 수정 제안)
- 추출 필드 테이블 (서류별 탭 · 신뢰도 표시)
- 환노출 3시나리오 + KB 상품 처방

이 한 화면에 전부 나옵니다. **LLM을 부르지 않아 1초 안에 끝나고, 인터넷이 끊겨도 동작합니다.** 발표 중 가장 안전한 경로입니다.

### ② 업로드 모드 — 진짜 AI 판독

`benchmark/cases/rendered/`의 PNG를 끌어다 놓으면 GPT-4o가 실시간으로 판독합니다. 10~30초 걸리고 서류 3장에 약 $0.06입니다.

> **말할 것:** "지금 보신 게 저장된 결과가 아니라, 방금 이미지에서 AI가 읽어낸 값입니다."

**🔴 업로드 전에 반드시 — 제시일을 입력하세요.**

파일을 고르면 그 아래 **`서류 제시(예정)일`** 칸이 있습니다. 여기를 비우면 **오늘 날짜**로 판정합니다.

시연용 서류는 과거 날짜로 발행돼 있어서, 오늘 기준으로 계산하면 **UCP600 14(c) 제시기한 경과**가
일괄로 잡힙니다. 그러면 샘플 모드에서 A였던 케이스가 업로드 모드에서 C로 나옵니다 — **같은 서류인데
다른 결과가 나오는 것처럼 보입니다.** 무대에서 가장 설명하기 곤란한 장면입니다.

| 업로드할 케이스 | 제시일 칸에 넣을 값 | 기대 등급 |
|---|---|---|
| `CLEAN-017_{lc,invoice,bl}.png` | **2026-06-30** | **A** (금액 6.9% 초과인데도 39A 과부족 허용으로 정상) |
| `DEFECT-019_{lc,invoice,bl}.png` | **2026-07-21** | **C** (금액 초과 + 서명자 자격 미표시) |

> 이 값은 각 케이스 JSON의 `presentation_date`와 같습니다. 실무에서도 제시일은 서류에 인쇄되지 않아
> 담당자가 정하는 값이므로, **입력칸을 두는 것이 옳은 설계**입니다. 심사위원이 물으면 그렇게 답하세요.
>
> 판정 결과 상단 칩에 `제시일 2026-06-30`이 찍힙니다. 비워두면 `제시일 미지정 — 오늘 기준 판정`
> 경고 칩이 뜨니, 화면만 봐도 어느 쪽인지 알 수 있습니다.

위 두 케이스의 PNG 6장은 **저장소에 포함돼 있습니다.** 나머지 114장은 용량 때문에 제외했고
`python3 render/render.py benchmark/cases/*.json --out benchmark/cases/rendered --png`로 재생성됩니다
(Playwright + chromium 필요).

**리허설 필수** — 업로드 모드는 네트워크와 API에 의존합니다. 실패에 대비해 샘플 모드를 먼저 보여주고, 업로드는 마지막에 하세요.

## 장면 3.5 — 수정 → 재심사 → 제출 가능 ★★ 핵심 (2분)

> **여기가 이 제품의 킥입니다.** 다른 팀은 "하자를 찾아준다"에서 끝나지만,
> TradeGuard는 **서류를 제출 가능한 상태로 만들어 놓고** 끝냅니다.
>
> 실동작 앱(`http://localhost:8000/`)에서만 가능합니다. 정적 화면에는 없습니다.

### 기준 케이스: **DEFECT-019** (완결 시나리오)

`DEFECT-019` 카드를 누르면 **등급 C · 65점 · 하자 2건**이 나옵니다.

1. **HIGH** 송장 금액 초과 → 하자 카드에 `247,104.00 → 225,280.00` 제안값이 이미 떠 있습니다 (신용장 :32B: 금액, 과부족 허용 없음)
2. **MEDIUM** B/L 서명자 자격 미표시 → `unclear → agent_for_carrier`

> **말할 것:** "이 제안값은 LLM이 만든 게 아닙니다. **신용장 32B·39A 기재값에서 코드가 계산한 것**입니다.
> 하자의 정의 자체가 '신용장과 다르다'니까, 정답은 이미 신용장 안에 있습니다."

**[이 수정 적용]** 을 두 하자 카드에서 각각 누르면 하단 바에 `2 / 2 선택됨`이 뜹니다.
**[수정 반영하고 재심사]** 클릭 →

| | 수정 전 | 재심사 후 |
|---|---|---|
| 등급 | **C** (65점) | **A** (100점) |
| 하자 | 2건 | **0건** |
| 예상 지연 | 7영업일 | **0영업일** |
| 환노출 | 8백만원대 | **0원** |
| 판정 | — | **✅ 제출 가능** |

> **말할 것:** "1초 만에, **LLM을 다시 부르지 않고**, 비용 0원으로 재심사했습니다.
> 판정도 제안도 결정적 규칙이라 같은 입력이면 항상 같은 결과가 나옵니다.
> 그리고 **누가 언제 어떤 값을 무엇으로 바꿨는지** 감사 이력이 리포트에 남습니다."

화면 하단 `감사 이력` 줄에 **엔진 커밋 해시 + 시각 + 수정 전후 값**이 찍혀 있는지 확인하세요.

### 이어서 보여줄 것: **DEMO-001** (정직성 장면, 30초)

`DEMO-001`은 **D · 40점 · 하자 3건**인데, 수정을 전부 적용해도 **C · 75점 · 1건**에서 멈춥니다.

> **말할 것:** "선적기일 경과는 이미 벌어진 사실이라 서류를 다시 써도 고쳐지지 않습니다.
> 저희는 **고칠 수 없는 걸 고쳤다고 말하지 않습니다.** 개설의뢰인 waiver나 신용장 조건변경이
> 필요하다고 남깁니다. 이 구분이 '서류를 아는 도구'와 '문자열을 바꾸는 도구'를 가릅니다."

**⚠️ 대본 주의 — 반드시 지킬 것**

- **"D → A"라고 말하면 안 됩니다.** 벤치마크 40건 어디에도 D→A 전이는 없습니다.
  실제 등급 전이는 **C→A 11건 · B→A 5건 · C→C 4건**입니다 (`benchmark/closedloop_report.md`).
- 완결 시나리오("제출 가능"까지 도달)를 보여줄 케이스는 **DEFECT-019**입니다.
- `DEMO-001`은 치유 불가 하자가 있어 **의도적으로** A에 도달하지 않습니다. 이건 결함이 아니라 설계입니다.

실측 재현:

```bash
cd benchmark && python3 evaluate_closedloop.py
```

| 지표 | 값 | 의미 |
|---|---|---|
| 하자 검출 F1 | **1.000** (TP 22 · FP 0 · FN 0) | 규칙 구현에 모순 없음 |
| 정상 오탐률 | **0%** (20건 중 0건) | 함정 정상 4건 포함 |
| 등급 일치율 | **100%** | A~D 판정이 정답과 일치 |

```bash
python3 crosscheck_independent.py | tail -5
```

> **40건 전부 라벨 == 독립검출. 우발 하자 0건.**

생성기와 **규칙을 공유하지 않는 별도 구현**으로 정답 라벨을 재검증한 결과입니다.

### ⚠️ 이 수치를 말할 때의 원칙

F1 1.000은 **규칙 구현 검증**이지 실서비스 성능이 아닙니다. 케이스 생성 규칙과 검출 규칙이
같은 UCP600 해석을 공유하므로, 이는 "성능"이 아니라 **규칙 구현에 모순이 없다는 검증**입니다.
실제 성능은 서류 이미지부터 시작하는 종단 평가 수치입니다.

| 종단 지표 (GPT-4o · 40건 / 120장) | 값 |
|---|---|
| 필드 추출 정확도 | **93.8%** (3,250 / 3,465 필드) |
| 문서 분류 정확도 | **100%** (120장) |
| 하자 검출 F1 | **0.889** (정밀도 87.0% · 재현율 90.9% · TP 20 · FP 3 · FN 2) |
| 등급 일치율 | **87.5%** (35 / 40) |

> ✅ **2026-07-31 현재 케이스 기준 재측정본입니다** (B-1R 완료 · 커밋 `3d87a3b`). PPT에 그대로 쓰십시오.

**"필드 정확도가 이전 95.5%에서 왜 내려갔나요?"** — 나올 만한 질문이고, 답이 유리합니다.

모델이 나빠진 게 아니라 **케이스가 어려워졌습니다.** 컨테이너 적재 대수 산출과 MT 포장수량
역산을 반영하면서 B/L에 `gross_weight`·`shipping_marks`가 새로 채워졌고, 이 두 필드에서만
오류가 17회·15회 납니다(이전 측정에는 0회 — 필드 자체가 없었습니다).
**서류를 더 실물에 가깝게 만들수록 추출은 어려워진다** — 이걸 숨기지 않고 말하는 편이 낫습니다.

> **말할 것:** "저희 벤치마크는 만들어 놓고 고정한 게 아니라, 사람이 렌더링된 서류를 눈으로 보면서
> 현실성이 떨어지는 부분을 계속 찾아 고쳤습니다. 그 결과 난이도가 올라가 수치는 내려갔지만,
> 이 숫자가 실제 서류에 더 가깝습니다."

**이 수치는 재현 가능합니다** — `benchmark/cases/extracted/`에 LLM 추출 결과 40건이 커밋돼 있어,
API를 다시 호출하지 않고도 검증할 수 있습니다.

```bash
# 저장된 추출값으로 하자 검출을 재현 (비용 0원)
```
