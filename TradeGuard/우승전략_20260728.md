## A. Executive Verdict

**"TradeGuard가 지금 해야 할 단 하나의 Kick은 '수정 → 즉시 재심사 → Before/After 등급 비교'의 폐쇄 루프(Closed-loop Discrepancy Resolution)다."**

이유: ① 기존 detect.py를 그대로 재호출하는 구조라 2~3일 내 완성 가능하고 실패 위험이 가장 낮다. ② "하자를 알려준다"에서 "제출 가능한 상태로 만든다"로 제품 정의가 바뀌어, 평가표의 활용 가능성·창의성·기술 적정성 세 항목을 동시에 끌어올린다. ③ 수정 제안값이 L/C 기대값에서 결정적으로 도출되므로 LLM 자유 생성 없이 재현 가능한 데모가 되고, 폐쇄 루프 통과율을 벤치마크 20건으로 제출 전에 실측할 수 있다.

## B. 현재 우승 가능성 진단 (냉정 채점)

### 1. 문제 정의 및 필요성 — 12 / 15
- 현재 수준: 강함. "서류 하자 → 대금 미회수"는 구체적이고, UCP600·MT700이라는 실제 규범에 근거한다.
- 강점: 목표 고객(수출 초보 중소기업·무역 담당자·은행 사전검토 직원)이 명시됨. 경쟁 2팀과 정면으로 다른 문제.
- 감점 요인: **"얼마나 자주, 얼마나 크게 발생하는가"의 공적 근거 인용이 없다.** 하자로 인한 지급 거절 비율 같은 업계 통계(예: ICC 조사에서 최초 제시 서류의 상당수가 하자 지적을 받는다는 류의 자료)를 출처와 함께 1장에 넣지 못하면 "그럴듯한 가정"으로 읽힌다.
- 즉시 보완책: ICC/무역협회/한국무역보험공사 공개 자료에서 하자 발생·지급거절 관련 통계 1~2개를 **출처 명기**로 확보. 확보 실패 시 "업계에서 반복 보고되는 문제" 수준으로 표현 수위 조절(수치 창작 금지).

### 2. 아이디어 활용 가능성 — 10 / 15
- 현재 수준: 보통. 프로토타입은 완성도가 높지만 **"누가, 업무 어느 지점에서, 어떤 절차로 쓰는가"가 문서화돼 있지 않다.**
- 강점: 샘플 모드(무료·오프라인)로 은행 내부망 제약을 우회하는 운영 감각을 보여줄 수 있음.
- 감점 요인: 사용 전/후 업무 흐름 비교가 없음. 고객용인지 행원용인지 사용 모델이 미확정.
- 즉시 보완책: **B2B2C 모델로 확정** — "KB 기업뱅킹 부가서비스로 수출기업이 제출 전 사전점검 → 결과 리포트를 행원이 참조". 근거: 역대 본선작 다수가 행원 업무 연결(문서 인포파인더, cheKB, LiivAssist)로 채택됐고, 매입 심사 앞단의 하자 감소는 은행의 재작업·미회수 리스크 감소로 직결됨. PPT 1장으로 As-Is/To-Be 업무 흐름도.

### 3. 아이디어 창의성 및 효과 — 13 / 20
- 현재 수준: 차별점은 실재하나 **"탐지에서 멈추는" 구조가 상한선.** 검출+조항 인용은 계약서 검토(cheKB)·규제 모니터링류의 기시감이 있다.
- 강점: 환율 예측기·금융 챗봇과 명확히 구별. "LLM 오판 실측 → 결정적 규칙 전환" 서사는 유일무이.
- 감점 요인: 데모 한 장면으로 "기존 방식보다 낫다"가 증명되지 않음 — 검출 결과 화면은 정적이다.
- 즉시 보완책: **Kick(폐쇄 루프)이 정확히 이 항목을 친다.** D등급 서류가 한 화면 안에서 제출 가능 상태로 바뀌는 Before/After가 "한 장면 증명"이 된다.

### 4. 기술 적정성 — 16 / 20
- 현재 수준: 가장 강한 항목. LLM(비정형 추출)과 결정적 규칙(금융 판정)의 역할 분리 + 분리 이유의 실측 근거 보유.
- 강점: 규칙 정합성 F1 1.000(규칙 자체)과 종단 F1 0.889(전체 파이프라인)를 **구분해서** 제시할 수 있는 팀은 드물다. 판정 재현성(LLM 키 유무 무관 동일 판정)을 테스트로 증명.
- 감점 요인: 추출 오류(4.5%)가 판정에 전파되는 경로에 대한 방어 설명 부족. 감사 이력(누가·언제·어떤 엔진 버전으로 판정했나)이 없음.
- 즉시 보완책: 폐쇄 루프의 부산물로 **판정 이력 JSON(입력 해시·엔진 버전·규칙 ID·시각)** 저장 — Passport 가설의 경량판을 흡수.

### 5. 개발 계획의 구체성 — 8 / 15
- 현재 수준: **최약 항목. 현재 구현 vs 향후 계획 구분 문서가 없다.**
- 감점 요인: 보안·운영·연계 계획 부재. 은행 도입 시나리오(내부망, 문서 반출 금지, 온프레미스 LLM 등) 미기술.
- 즉시 보완책: PPT 2장 할당. ① 단계 로드맵(현재: 사전점검 프로토타입 → 1단계: KB 기업뱅킹 파일럿 → 2단계: 매입 심사 보조 → 3단계: SWIFT 연동), ② 운영 제약 대응(온프레미스/사내 LLM 대체 가능한 프로바이더 추상화가 이미 구현돼 있음을 근거로 제시 — llm.py 추상화가 여기서 점수가 된다).

### 6. 기술 실현 가능성 — 13 / 15
- 현재 수준: 강함. 실동작 SPA + 원커맨드 데모 + 통합 테스트 29항목 + 정량 지표.
- 강점: 샘플 모드로 심사위원이 API 키 없이 3분 내 실행 가능.
- 감점 요인: 벤치마크 40건이 전량 합성 데이터라는 한계 명시가 문서에 약함. 업로드 경로(B-4)가 미실측 상태면 "실제로 동작하는가"에 구멍.
- 즉시 보완책: B-4 실측(~$0.06) 완료 + 한계 명시 섹션("합성 데이터 기반, 실서류 검증은 파일럿 단계 과제")을 README·PPT에 추가. 한계를 숨기지 않는 것 자체가 이 항목의 채점 질문이다.

## C. 역대 진출작(1~7회) 대비 포지셔닝

### 1. 강한 출품작의 공통 성공 구조
역대 본선작 55건을 구조로 분석하면 반복되는 골격은 다섯 가지다.

1. **문서 × 규칙 × 근거 제시**: 계약서 독소조항 검토(cheKB, 4회), 금융상품 약관 자동 분류(1회), 규제·법규 준수 모니터링(7회) — 비정형 문서를 구조화하고, 판정 근거를 조항 단위로 제시하는 유형이 꾸준히 본선에 오름.
2. **설명 가능성의 전면화**: XAI 대출심사 "AI에게 이유를 묻다"(3회), 설명 가능한 신용위험 모니터링(7회, "AI 판단 근거와 데이터 출처를 투명하게 공개") — 최근 회차일수록 '왜'를 보여주는 팀이 선정됨.
3. **행원 업무에 꽂히는 도구**: KB 문서 인포파인더(2회), LiivAssist(4회), 상담사 지원(6회) — "은행이 도입할 이유"가 업무시간·리스크 단위로 명확한 작품.
4. **탐지형 서비스의 강세**: 보이스피싱 탐지(3·5·6회 반복 진출), 사기 거래 탐지(6회), 자금세탁 탐지(5회) — 금융 손실을 '사전에 막는' 포지션이 심사에 잘 통함.
5. **좁은 문제 + 완결된 시연**: 넓은 플랫폼형보다 한 문제를 끝까지 푼 작품이 다수(영수증 OCR 가계부, 약관 아이트래킹 등).

### 2. TradeGuard가 이미 충족한 구조
- ①번을 정확히 관통: L/C·송장·B/L 구조화 + UCP600/MT700 조항 인용. 역대 어느 작품도 무역서류 도메인은 다루지 않아 **소재 중복이 없다.**
- ②번 충족: 판정 근거·조항 인용·결정적 재현성. "LLM 오판 실측 → 규칙 전환"은 역대작에 없던 수준의 설계 근거.
- ④번 충족: 대금 미회수라는 금융 손실의 사전 차단 포지션.

### 3. 아직 채우지 못한 구조
- ③번 미충족이 최대 격차: **은행 업무와의 접점이 문서화돼 있지 않다.** 역대 통과작은 예외 없이 "은행의 어떤 업무가 어떻게 바뀌는가"를 답했다.
- ⑤번의 '완결': 탐지까지는 완결이나 업무 완료(제출 가능 상태 도달)는 아직 아니다. → Kick이 채운다.

## E. 최종 Kick 상세 설계 — Closed-loop Discrepancy Resolution

### 사용자 시나리오
1. 수출기업 담당자가 매입 신청 전, L/C·상업송장·B/L 3종을 업로드(또는 샘플 선택).
2. 추출 결과 확인 → 하자 리포트: 등급 D, 하자 3건, 각 건에 UCP600 조항·MT700 필드 근거와 **수정 제안값**(L/C 기대값에서 결정적으로 도출) 표시.
3. 담당자가 하자별로 제안값을 검토하고 "적용"을 클릭하거나 직접 수정 — **자동 반영이 아니라 사람이 승인하는 구조**(human-in-the-loop).
4. "재심사" 클릭 → detect.py 재실행(1초 내) → Before/After 비교 화면: D → A, 하자 3 → 0, **"제출 가능"** 배지.
5. 판정 이력(수정 전후 값·규칙 ID·엔진 버전·시각)이 포함된 사전점검 리포트를 PDF 저장 → 은행 제출 시 첨부.

### 데모 화면 (신규 1개 + 기존 수정 2개)
| 화면 | 사용자가 보는 것 | 행동 | 시스템 반응 | 심사위원 메시지 |
|---|---|---|---|---|
| 하자 리포트(기존 확장) | 하자 3건 + 조항 근거 + 수정 제안값 | 제안 "적용" 클릭 | 필드값 변경 표시(취소선→새값) | 근거 있는 수정 제안, 사람이 승인 |
| 재심사 진행(신규) | "재심사 중" 상태 | "재심사" 클릭 | 결정적 엔진 재실행 <1초 | LLM 재호출 없음 = 무료·재현 가능 |
| Before/After(신규) | 등급 D→A, 하자 3→0, 잔여 하자 목록(있다면) | PDF 저장 | 판정 이력 포함 리포트 생성 | **업무가 완료됐다** |

### 백엔드 변경
- 신규 API: `POST /api/redetect` — 입력: `{case: 수정 반영된 문서 JSON, edits: [{doc, field, before, after}]}`, 출력: `{report: 기존 discrepancy_report 스키마, before_grade, after_grade, resolved: [], remaining: [], history_id}`.
- 재사용: detect.py 판정 함수 그대로 호출(수정 없음). 수정 제안값은 기존 검출 로직이 이미 비교하는 "기대값(L/C 측)"을 응답에 노출하는 것뿐 — **detect.py의 불일치 판정이 곧 제안 생성기**다.
- 새 데이터 구조: `audit_history.json` — {history_id, timestamp, engine_version(git hash), input_hash, edits[], before/after 등급·하자}.
- 예외 처리: 수정 불가능 유형(예: 선적기일 경과)은 제안 없이 "수정 불가 — 은행 협의 필요" 라벨 → 잔여 하자로 남김. 이게 오히려 정직성 점수가 된다.
- 외부 API 없이 시연: 재심사는 원래 LLM을 안 쓴다. 샘플 모드 그대로 동작.

### 프론트엔드 변경
- 하자 카드에 제안값 + [적용] 버튼(제안 없는 유형은 입력 필드), 상단에 [재심사] 버튼.
- Before/After: 등급 배지 2개 나란히 + 화살표, 해소 하자는 취소선 처리, 잔여 하자는 상단 고정.
- 수정 체크리스트와 연결: 체크리스트 항목 = 하자 카드와 1:1, 적용 시 자동 체크.
- 접근성: 등급 변화를 색상+텍스트("D 위험 → A 적합")로 병기, 적용/재심사 버튼 포커스 표시(기존 디자인 시스템 준수).

### 평가 방법 (제출 전 실측 계획 — `benchmark/evaluate_closedloop.py` 신규)
| 지표 | 방법 | 상태 |
