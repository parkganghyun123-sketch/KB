## D. Critical 및 High 결함

### P0-1 · **High** · PPT 9장 "LLM 호출은 판독 1회뿐입니다"

**위치**: PPT 슬라이드 9 좌측 단락 / 대응 코드 `server/app.py` 473·519·529행

**문제**: 서류 1장당 실제 LLM 호출은 **2회**입니다.

```
server/app.py:519    doc_type = classify(client, blocks)      ← 1회차
server/app.py:529    data, retries = extract_doc(...)         ← 2회차
server/app.py:473    dt = classify(client, [image_block(dest)])  ← UI 사전 판별 (추가 1회)
```

UI에서 파일을 올리면 뱃지 표시용 사전 판별이 먼저 돌기 때문에, **화면상 흐름 기준으로는 3회**입니다.

**영향**: 아키텍처 슬라이드의 핵심 주장이 코드와 정면으로 어긋납니다. 심사위원이 `app.py`를 grep 한 번 하면 나옵니다. 이 프로젝트는 "정직함"이 유일한 차별점이라 **이 한 건이 나머지 수치의 신뢰도까지 끌어내립니다.**

**수정안**: 슬라이드 9 문구를

> "LLM 호출은 **판독 단계에만** 국한됩니다. 서류 1장당 종류 판별 1회 + 필드 추출 1회이며, **판정·수정 제안·재심사에는 0회**입니다."

로 교체. 오히려 "구간을 나눴다"는 원래 주장이 더 선명해집니다.

**예상 작업량**: 15분 이내

### P0-3 · **High** · 업로드 파일명 경로조작

**위치**: `server/app.py` 465행(`classify_upload`), 512행(`analyze_upload`)

```python
dest = tmp / (f.filename or "upload.png")     # 512행
name = f.filename or "upload.png"; dest = tmp / name   # 465행
```

**문제**: `f.filename`은 **클라이언트가 정하는 값**입니다. 검증 없이 경로 결합에 씁니다.

실제로 확인했습니다.

```
'../../tmp/ESCAPED.png'  →  /tmp/tg_demo/../../tmp/ESCAPED.png
'/tmp/ABSOLUTE.png'      →  /tmp/ABSOLUTE.png      ← 임시 디렉터리를 완전히 벗어남
```

임시 디렉터리 밖에 파일이 실제로 생성되는 것도 격리 환경에서 재현했습니다.

브라우저는 경로를 떼고 보내므로 **정상 사용에서는 발생하지 않습니다.** 그러나 `curl`이나 스크립트로는 임의 경로에 씁니다. 서버 프로세스 권한 범위에서 **파일 덮어쓰기**가 가능합니다.

**영향**: `case_id`는 화이트리스트로 막아 놓고(`CASE_ID_RE`) **업로드 파일명은 안 막은 비대칭**입니다. 보안 검토자에게는 "한 곳은 알고 막았는데 다른 곳은 놓쳤다"로 읽힙니다.

**수정안**: 파일명을 신뢰하지 말고 서버가 생성.

```python
from pathlib import PurePosixPath
safe = PurePosixPath(f.filename or "upload.png").name      # 경로 성분 제거
ext  = Path(safe).suffix.lower()
if ext not in (".png", ".jpg", ".jpeg", ".webp"):
    ...  # 기존 오류 처리
dest = tmp / f"{i:02d}{ext}"        # 서버가 이름을 정한다
```

원래 파일명은 화면 표시용으로만 응답에 담고, 디스크 경로에는 쓰지 않습니다.

**기존 기능 영향**: 없음. `classified[].filename`은 표시용이므로 원본 이름을 그대로 넣으면 됩니다.

**최소 테스트**:
```bash
curl -X POST localhost:8000/api/classify -F "files=@x.png;filename=../../ESCAPED.png"
# → 200 이면서 /tmp 밖에 파일이 생기지 않아야 함
bash test_all.sh    # 45/45 유지 확인
```

**예상 작업량**: 15분 이내

### P1-1 · **Medium** · 업로드 크기·개수 제한 없음

**위치**: `server/app.py` `analyze_upload` / `classify_upload`

**문제**: 파일 크기, 개수, 이미지 해상도 제한이 없습니다. 100MB 이미지 50장을 보내면 전부 메모리에 base64로 적재됩니다(`image_block`). LLM 비용도 그만큼 나갑니다.

**영향**: 로컬 프로토타입이라 실사고 위험은 낮지만, 심사위원이 "서비스로 올리면?"이라고 물었을 때 답이 없습니다.

**수정안**: 상단에 `MAX_FILES = 10`, `MAX_BYTES = 10 * 1024 * 1024` 상수를 두고 초과 시 413 반환. UI에도 안내 문구 추가.

**예상 작업량**: 15분 이내

### P1-2 · **Medium** · 입력 검증이 서비스 가용성 검사보다 뒤에 있음

**위치**: `server/app.py` 429~449행

**문제**: `analyze_upload`에서 LLM 키 확인(503)이 **제시일 형식 검증보다 먼저** 실행됩니다. 실측했습니다.

```
잘못된 제시일 2026-13-99 + 키 없음  →  503 "LLM 키가 없습니다"
                                        (400 형식 오류가 아님)
```

**영향**: 사용자가 날짜를 잘못 넣었는데 "키가 없다"는 무관한 메시지를 받습니다. 실사용 시 혼란.

**수정안**: 입력 검증(400)을 `get_client()` 앞으로 이동.

**예상 작업량**: 15분 이내
